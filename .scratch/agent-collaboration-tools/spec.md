# Agent 协作工具简化

Status: ready-for-agent

规格日期：2026-11-20。行为设计与目标 prompt 已确认，待实现。本规格发布到项目本地 Markdown tracker，不表示代码已经实现或服务已经部署。

## Problem Statement

用户希望把工作交给协调者后，协调者能够组织 Worker、接收进展和成果，并继续推动工作。当前交互规则分散在普通回复、显式汇报、成果登记、群公告和任务收尾等多条路径中，调用条件难以理解，容易出现 Worker 已完成工作，但协调者没有收到继续处理的信号。

此前调查确认，运行实例中的普通 Worker 最终回复只保留在任务内，正式汇报又要求用户在 Worker 群里明确提出。Worker 默认没有群，协调者也没有定时巡查，用户因此需要反复询问进度来推动后续工作。新增的成果通知另设登记和等待轮次成功结束的规则，继续增加了协作复杂度。

用户希望 Agent Loop 提供清晰、可靠的工具，由 AI 根据 prompt、项目规则和上下文判断何时使用。用户同时希望 Worker 群保留 Codex CLI 式的直接交流体验，协调群只展示协调者主动选择发送的内容。

## Solution

统一梳理整个协作工具层，包括创建 Worker、建群、通信、群消息、状态查询、定时自我唤醒、任务结束和资源清理。

采用两个独立消息工具。Agent 消息工具只在协调者与其项目内 Worker 之间双向传递内容；群消息工具向当前角色关联的群发送供人阅读的内容。Worker 之间不能直接通信，也不能创建 Agent Loop Worker。Worker 内部继续使用 pstack 子 agent 组织并行工作。

Agent 消息发送后即可交给接收者处理，不等待发送者结束本轮。Worker 通过 prompt 获得主动反馈进展、阻塞、重要变化和成果的指导，不再需要用户在任务群额外要求汇报。协调者根据收到的消息继续组织工作，并可自行安排一次性唤醒来跟进等待事项。

Worker 可以为自己建群，协调者也可以为 Worker 建群。已有群复用。Worker 群默认展示完整助手过程说明、问题和最终回复；协调者通过群消息工具选择发送哪些内容，包括对用户直接提问的回复。

任务结束与资源清理拆成独立动作。结束只标记当前约定工作完成或终止，不自动删除文件。新消息可以唤醒已结束任务的原 Worker，在原上下文继续处理。是否创建新任务、何时清理资源，由 AI 根据工作需要判断。

删除派单工具对 Feature 授权消息、Issue 版本和调查模式的业务检查。业务规则放入 prompt；Runtime 保留调用身份、项目归属、已确认的角色边界、可靠投递、持久化恢复和实际资源约束。

## User Stories

1. 作为项目用户，我希望把工作交给协调者后由它继续跟进，以便无需反复询问进度才能推动任务。
2. 作为项目用户，我希望业务流程由 AI 根据 prompt 和上下文判断，以便调整工作方式时不必修改 Runtime 的业务状态机。
3. 作为协调者，我希望查询已有任务、记录和成果，以便恢复上下文并避免重复派单。
4. 作为协调者，我希望创建带完整任务说明和执行配置的 Worker，以便把具体工作交给合适的执行者。
5. 作为 Worker，我希望使用 pstack 内部子 agent 组织并行工作，以便无需创建额外的 Agent Loop Worker。
6. 作为项目用户，我希望只有协调者可以创建 Agent Loop Worker，以便项目任务组织保持明确的归属。
7. 作为协调者，我希望直接向自己的 Worker 发送指令和补充信息，以便及时调整工作。
8. 作为 Worker，我希望主动向协调者发送问题、进展和成果，以便不依赖用户额外要求汇报。
9. 作为无群的 Worker，我希望仍能给协调者发消息，以便建群不会成为内部协作的前提。
10. 作为发送者，我希望消息发送后接收者就可以处理，以便双方不必等待发送者本轮结束。
11. 作为正在执行的接收者，我希望新消息追加到当前工作中，以便及时处理变化。
12. 作为空闲的接收者，我希望新消息在原会话启动一轮，以便保留既有上下文。
13. 作为发送者，我希望情况变化后可以补充更正消息，以便接收者根据新事实调整工作。
14. 作为协调者，我希望 Worker 之间的协作经我处理，以便掌握跨任务依赖和安排。
15. 作为项目用户，我希望消息不能越过项目归属或冒用其他发送者，以便不同项目的工作不被混入。
16. 作为发送者，我希望重试和服务恢复不会造成同一操作重复执行，以便消息、任务和群不会重复创建。
17. 作为 Worker，我希望需要与用户讨论时可以为自己建群，以便不必等待协调者代为操作。
18. 作为协调者，我希望可以为指定 Worker 建群，以便安排用户直接参与任务讨论。
19. 作为任务群用户，我希望重复建群请求复用已有群，以便对话保持连续。
20. 作为任务群用户，我希望默认看到完整的助手过程说明、问题和最终回复，以便获得类似 Codex CLI 的交流体验。
21. 作为任务群用户，我希望普通回复无需额外调用发送工具也能显示，以便不会因模型遗漏调用而丢失正常对话。
22. 作为协调者，我希望分别选择给 Agent 发消息和给人发群消息，以便内部协调与面向用户的交流各有明确用途。
23. 作为项目用户，我希望协调群由协调者选择发送内容，以便内部通信不会自动刷满群聊。
24. 作为项目用户，我希望直接提问后收到协调者通过群消息工具给出的回复，以便回答确实出现在群里。
25. 作为 Worker，我希望将影响项目安排的用户决定及其来源发给协调者，以便协调者掌握实际变化。
26. 作为 Agent，我希望为自己设置带时间和内容的一次性提醒，以便稍后检查等待事项。
27. 作为 Agent，我希望查看并取消自己不再需要的提醒，以便避免过期事项继续打断工作。
28. 作为项目用户，我希望没有设置提醒时系统不会固定周期催办，以便跟进节奏由 AI 根据工作决定。
29. 作为 Agent，我希望服务恢复后提醒仍能被处理且不会重复触发，以便跟进不依赖进程持续在线。
30. 作为暂停任务的用户，我希望消息和到期提醒先被保存，以便任务不会被自动解除暂停。
31. 作为协调者，我希望单独记录任务结束，以便完成状态不隐含文件删除。
32. 作为用户，我希望任务结束后可以继续向原 Worker 提问或追加工作，以便沿用原有上下文。
33. 作为协调者，我希望根据工作内容决定是否另建任务，以便小范围后续工作不被强制拆成新任务。
34. 作为协调者，我希望单独决定何时清理任务资源，以便完成后仍能保留现场供复查。
35. 作为项目用户，我希望清理只涉及归属明确且可释放的任务资源，以便原始资料、共享资源和仍在使用的目录得到保留。
36. 作为 Worker，我希望清理与执行不会同时使用同一资源，以便继续工作时不会遭遇正在运行的目录被删除。
37. 作为 Worker，我希望文件清理后仍能继续原会话并获知实际资源状态，以便按需要重新准备工作目录。
38. 作为协调者，我希望派单不必提供特定群消息 ID、Issue 版本或业务模式字段，以便依据已有指示与项目规则决定工作安排。
39. 作为项目用户，我希望只讨论、只调查以及其他明确限制保留在 prompt 和任务说明中，以便移除工具检查后 AI 仍遵守约定。
40. 作为 Worker，我希望任务说明包含目标、背景、范围、已有决定、验收和交付要求，以便能够自主组织工作并提供可核查成果。
41. 作为协调者，我希望 Worker 主动通知成果并附上实际证据，以便继续验证和交付，而不是把普通最终回复当作已完成交接。
42. 作为维护者，我希望公共角色 prompt、项目规则和动态上下文一致，以便不会同时向 AI 注入相互矛盾的新旧指令。
43. 作为现有实例的用户，我希望迁移保留任务、Thread、群、执行身份、暂停状态和历史记录，以便升级不重派已有工作。
44. 作为现有实例的用户，我希望历史最终回复不会被批量转换为新消息，以便升级不会突然触发重复工作。

## Implementation Decisions

1. **职责划分。** AI 判断工作内容、阶段、授权是否充分和调用时机。Runtime 执行参数与调用身份校验、归属约束、可靠投递、持久化和恢复。移除业务检查不取消本规格明确保留的角色权限与项目边界。

2. **角色和通信关系。** 只有协调者可以创建本项目的 Agent Loop Worker。Worker 内部子 agent 由 pstack 管理。Agent 消息只允许协调者与其 Worker 双向通信，不允许 Worker 之间直连或跨项目通信。

3. **工具职责。** 以下是能力边界，具体命名与参数在实现时统一。两个消息用途必须以两个独立工具暴露。

   | 能力 | 调用边界与行为 |
   | --- | --- |
   | 创建 Worker | 协调者提供任务说明与允许的执行配置，创建并启动本项目任务。 |
   | Agent 间发消息 | 协调者与其 Worker 互发正文和必要引用，送入对方执行输入。 |
   | 向群发消息 | 发往当前角色关联的群，内容供人阅读，不代替 Agent 间通知。 |
   | 建立 Worker 群 | 协调者为 Worker 建群，或 Worker 为自己建群，已有群复用。 |
   | 查询状态与记录 | 沿用项目和任务归属，查询活动、消息、成果和历史上下文。 |
   | 定时自我唤醒 | 为自己设置一次提醒，支持查询和取消。 |
   | 记录任务结束 | 协调者记录当前工作完成或终止，不附带资源删除。 |
   | 清理任务资源 | 显式清理指定、归属明确的任务资源，并返回实际结果。 |
   | 暂停、恢复和其他管理 | 保留已有必要能力及项目归属边界，不扩大跨项目操作范围。 |

4. **消息时机与含义。** 接受发送后立即进入持久投递流程，不等待发送者完成当前轮次。运行中的接收者追加输入，空闲接收者在原 Thread 开始一轮。回执表示工具接受或送达的实际状态，不表示接收者已接受结论或完成任务。发送者后来失败不会撤回已经送达的消息，应发送后续更正。

5. **群消息体验。** Worker 群保留完整助手输出的默认转发，不要求逐条使用群消息工具。协调者普通答复不再按输入来源自动进入协调群；包括直接回复用户在内的内容，由协调者主动使用群消息工具发送。取消重复的旧公告路径，避免一次主动发送再自动补发相同答复。原生问题、审批、权限请求及 Runtime 异常保留必要通知渠道。

6. **主动协作。** Worker prompt 要求在阻塞、重要变化、需要协调或完成成果时主动联系协调者。普通最终答复、保存记录和给人的群消息均不替代 Agent 通知。协调者 prompt 要求收到消息后判断下一步，并在需要回访时安排提醒。这些是 AI 的工作指导，不新增 Runtime 的业务阶段状态机。

7. **定时自我唤醒。** 持久保存提醒归属、触发时间、内容及是否已触发或取消。到期后通过现有输入投递机制交给同一个 Agent。未设置时不产生定时监督事件。重试、取消与服务恢复须收敛到同一个提醒结果，避免重复唤醒。

8. **暂停和恢复。** 暂停与任务结束分别表示不同状态。暂停期间的新消息和到期提醒先保存，显式恢复后处理，不自动解除暂停。沿用现有未知投递回执对账能力，不以盲目重发消除不确定状态。

9. **任务结束和后续输入。** 当前工作是否完成与 Agent 是否正在执行分开记录。结束保存结论及历史摘要，不能永久封闭原任务。后续新输入可以启动原 Worker，更新当前工作状态并保留前次完成记录。是否另建任务由协调者判断。

10. **清理独立执行。** 结束任务不创建清理操作。AI 单独调用清理工具时，Runtime 检查资源身份、归属、实际占用和并发使用。清理期间先保存新输入，资源状态确定后继续处理。已经删除的文件不伪装为存在；继续会话时提供实际状态，由 Agent 按需通过资源工具准备新的工作目录。

11. **派单业务检查迁移到 prompt。** 删除 Feature 实现派单对特定项目群所有者消息、Issue 版本、范围指纹和调查模式的强制检查，不再由 Runtime 根据业务类型追加调查限制。协调者依据用户指示、已有授权和项目规则判断调查还是实现，并将允许和禁止范围写进任务说明。用户明确的只讨论或只调查限制、外部提案不自动成为开发授权等规则，由 prompt 承载。

12. **Prompt 组成。** 协调者和 Worker 各有一份固定角色 prompt，另注入项目身份、执行配置、项目专属规则与最新记录。每次派单补充目标、背景、范围、已有决定、验收和交付要求。这些内容是写作指导，不变成工具强制校验的业务字段。具体工程流程与独立验证由 pstack 和项目约定指导，不增加第三种 Agent Loop 角色。

13. **Prompt 一致性。** 迁移角色正文、动态角色说明、工具定义、客户端入口和已有派单中的 Runtime 使用说明。保留任务目标和真实用户决定，移除要求用户先在 Worker 群请求汇报、报告路由分类、成果等待轮次成功结束以及已结束任务必须另建任务等冲突指令。仅修改两份角色文件不算完成。

14. **数据和旧能力迁移。** 持久模型需要表达统一协作消息、面向人的群消息、一次性提醒、可继续的任务完成记录和独立清理操作。保留已有任务、Thread、群、执行配置与来源、记录和暂停状态。迁移调用方后删除被替代的 report 路由和 deliver_result 待交付状态机。旧记录保留可查询；已登记但未处理的投递逐项对账，不批量重放历史最终回复。

15. **影响的模块。** 项目协作工具及角色校验、运行循环和输入投递、持久存储、执行后端工具适配、任务群和群消息投递、任务结束及资源清理、角色提示词与动态上下文、相关状态查询与看板呈现都需要保持新契约一致。优先复用现有执行输入与恢复机制，不另建平行的消息运行系统。

16. **保留的边界。** 本规格不改变模型执行配置的选择与保持规则、GitHub 收集条件、原生工具审批或真实资源归属。项目记录和其他管理能力沿用现有职责，去掉与已确认流程冲突的编排，不借重构引入新的跨项目权限。

## Testing Decisions

1. **主要测试接缝。** 优先从 AgentLoop 对外工具入口和群输入入口驱动完整 Runtime，观察接收 Agent 的执行输入、用户可见群消息、状态查询结果与真实资源变化。主流程复用现有项目 Runtime 集成夹具和真实 SQLite 存储，只对外部执行后端、飞书和 GitHub 使用可控替身。无需为每个内部辅助函数新增测试接缝。

2. **复用先例。** 现有项目 Runtime 测试已覆盖协调者派单、群创建、消息投递、丢失回执、暂停和重启；任务收尾测试已使用真实文件、Git 工作树与子进程验证占用和删除；执行后端协议测试已验证保留 Thread 的工具调用与恢复。新增行为在这些层扩展，替换锁定旧业务规则的断言，同时保留来源、去重、隔离和资源保护覆盖。

3. **测试质量。** 断言用户或工具调用者能观察到的结果。不要仅断言内部函数调用次数、复制分支判断或依靠 prompt 中出现某个词证明模型行为。测试 fixture 成功不代表真实 Agent 或真实飞书交互已经通过。

4. **确定性的时间控制。** 定时提醒在主 Runtime 测试接缝内使用现有可控时间方式推进时间，验证未到期、到期、取消、重复扫描和重启。无需依赖长时间实际等待，也不为提醒另造一套测试调度系统。

5. **完整验收矩阵。**

   | 场景 | 可观察的通过条件 |
   | --- | --- |
   | 无群 Worker 主动通信 | 无用户汇报请求也能向协调者送达消息，并启动或追加协调者执行输入。 |
   | 发送者仍在执行 | 协调者已经收到消息时，Worker 原轮次仍可继续；之后失败不撤回已送达消息。 |
   | 双向通信和边界 | 协调者与自己的 Worker 双向成功；Worker 之间、跨项目消息及 Worker 创建 Agent Loop Worker 被拒绝。 |
   | 投递重试与恢复 | 同一操作在重试、丢失回执和服务恢复后不产生重复任务、消息或群；未知结果先对账。 |
   | Worker 自行建群 | 可为自己创建并复用群，群内默认显示完整助手过程说明、问题和最终回复。 |
   | 两类消息分离 | Agent 消息不会直接刷协调群；给人的群消息不会冒充对另一个 Agent 的输入。 |
   | 协调群显示 | 协调者主动调用群消息工具后用户可见，直接用户提问也通过该工具回复，普通最终答复不重复播报。 |
   | 一次性提醒 | 到期触发一次，可查询和取消，未设置时不产生定时监督，服务恢复后不丢失或重复触发。 |
   | 暂停期间输入 | 新消息和到期提醒保存但不执行，恢复后继续原任务。 |
   | 结束后续接 | 记录结束后文件保留，新消息继续原 Worker 和 Thread，前次完成记录可查询。 |
   | 独立清理 | 只在显式请求后清理指定资源；正在使用、原始或其他任务的资源不被误删。 |
   | 清理与后续输入 | 清理进行中不会启动冲突的资源使用；文件已清理后原会话仍能获得后续输入和实际资源状态。 |
   | 派单业务字段 | Feature 派单无需特定用户消息或业务模式字段；固定 prompt 与任务说明仍传达实际用户限制。 |
   | Prompt 组合 | 活动与恢复会话得到一致的新角色说明，旧汇报限制与新消息规则不同时注入。 |
   | 旧数据迁移 | 项目成员、Thread、群、执行身份、历史和暂停状态保留，不重派任务或批量重放历史 final。 |

6. **真实协作验收。** 复用已有真实 Codex 协调者探针的方式，在隔离任务中验证 Worker 实际调用 Agent 消息工具、协调者收到后执行下一步，以及定时唤醒后的真实继续。该先例的飞书部分使用替身，因此另需在授权的测试群检查 Worker 默认输出和协调者主动群消息。证据记录实际版本、工具调用、收件结果、群消息和后续动作。

7. **运行验证的边界。** 测试群、执行后端或环境不可用时，标记相关验收为受阻，不能用模拟测试替代通过结论。规格阶段只确定方法，不启动服务、不发群消息、不执行清理或部署。

## Out of Scope

- Worker 创建 Agent Loop Worker，或 Worker 之间直接通信。
- 跨项目 Agent 通信和资源操作权限扩展。
- Runtime 固定周期催办、自动推断完成、自动批准开发或自动编排验收流程。
- 将所有 Worker 普通最终回复自动转成协调者消息，或将内部通信自动转发到协调群。
- 改变 pstack 内部子 agent 的创建与调度，新增 Agent Loop verifier 角色。
- 修改模型执行配置体系、GitHub 收集规则或原生工具审批机制。
- 因升级自动重派历史任务、恢复用户暂停的工作，或批量重放历史最终回复。
- 自动清理用户原始资料、共享目录或其他任务资源，以及默认删除远端资源。
- 在本次规格发布中实现业务代码、修改运行实例、部署或重启服务。
