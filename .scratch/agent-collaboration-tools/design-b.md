# Agent Loop collaboration design B

The coordinator and its Workers choose when to share an update, send a group reply, schedule a follow-up, record completion, and release resources. A Worker can deliver evidence to its coordinator while its own turn is still running. This package covers tickets 01 through 08 against b053f4d.

## Components

- CodexAppServer binds the dynamic tool call to a live Thread, turn and connection epoch. WorkspaceBridge binds the retained-Thread shell fallback to a server-issued task capability. Both currently dispatch through AgentLoop.projectAction and ProjectRuntime.action. New Threads receive tool definitions at creation. The resume request supplies developer instructions only. See src/adapters/codex.ts, src/ports.ts, src/project-client.ts and src/workspace-bridge.ts.
- ProjectRuntime owns project membership, per-caller request fingerprints and receipts. ProjectLedger already persists the facts in SQLite. Store.receive assigns an inbox sequence to each unique delivery ID. AgentLoop advances input through startTurn or steer and reconciles uncertain acknowledgements against seenInputIds. TaskGroups owns group creation and binding generations. WorkerChatTurn already publishes ordinary Worker output through the outbox.
- TaskCloseout snapshots owned resource identities, seals scopes for cleanup and tracks destructive progress. Its current accept method also records completion and schedules every remaining scope for deletion. AgentLoop.advance and recover currently forward subsequent owner input to the coordinator. The current completion policy reaches into Codex native requests.

## Flow

1. Decode the named tool and arguments once, preserve its transport-authenticated caller, and validate role and recipient through ProjectLedger. Recheck active turn identity inside the mutation lane. A model-supplied source reference is supporting material. A referenced owner message resolves to its actual stored input, author and group.
2. Atomically commit the accepted local effect and request receipt. For Agent messages this is the recipient inbox row. For group messages it is the task outbox row and its pinned group binding. Return the delivery ID and current state. Release the project lane, then schedule the existing recipient task lane promptly. Network acknowledgements and downstream model execution never hold the sender's project lane. Restart recovers committed rows even if the process exited before scheduling.
3. A running recipient gets a steer. An idle recipient starts another turn on its saved Thread. Paused recipients keep their input until explicit resume. At delivery, preserve the native question association rules for coordinator answers to a Worker, and the distinct approval and permission channels. The group send schedules the outbox flush only. A retry reads the current transport state through the original delivery ID.
4. An existing tick claims due reminders in SQLite and enqueues each for its owner. A completed Worker reopens on accepted fresh owner, Agent or due self-reminder input. An active destructive window defers execution. The resources shown in its next input reflect what survived or was removed.

## Boundaries and alternatives

**Selected shape.** Use separate top-level protocol names for Agent and human sends, each accepting its own strict Zod argument schema. Keep project_action for other project operations. One internal discriminated command represents each validated call for ProjectRuntime, including calls through the fallback. Keep the existing inbox and outbox as delivery state authorities. Add an indexed reminders table, since the runtime needs a cross-project due-time lookup. For historical message listings, use the existing inbox provenance and outbox binding metadata, with indexed lookup by the verified visible member IDs when needed. A stable receipt points at the row. Persisting a second copy of delivery status would require dual writes for every acknowledgement.

**Alternate shape.** A project-wide collaboration journal can store all intents with a sequence and hand them to independent Codex, Feishu, reminder, and cleanup consumers. It simplifies a unified timeline and permits consumer replay. Here it would also require reconstructing inbox unknown acknowledgements, group generation checks, process guards and completed histories or projecting them back into the existing owners. The added journal replay position presents a second duplicate-delivery boundary. A single read-side projection can supply the required timeline using the selected shape.

**Red-flag screen.** The caller supplies a recipient only for Agent messages and scope IDs only for cleanup. A single schema per tool derives wire parameters, fallback parsing and internal types. Runtime checks permissions once downstream of both transports. Keep sender identity, group generation, resource identity and actual status internal to their existing owners. Remove replaced action names from the strict project_action schema and both launch paths, including scripts. Preserve historical decoding outside the callable API. This removes parallel routes, pass-through wrappers and hand-maintained tool-name lists.

## Gotchas

- Store.receive currently labels project events as source input. Add explicit provenance for Agent messages and reminders, and recognize them at failure-recovery and completed-task boundaries. Reusing all source events as wake signals would revive tasks on GitHub collection and migration. AgentLoop currently resumes certain legacy paused tasks on owner input. Preserve explicit pause for migrated project Workers across every producer.
- ProjectRuntime's old action receipt returns a historical acceptance snapshot. A stable retry after a failed acknowledgement must still expose the live row state. Use the same fingerprint on native and shell entry points. Continue rejecting the same request ID with changed content, including a change of tool.
- Plain FeishuPort.send validates message_id, then discards it. AgentLoop.flush holds generic uncertain sends indefinitely. Persist the returned Feishu message ID when provided. Pin chat ID and binding generation in the same transaction as explicit group output. Use the existing stable send UUID for safe reconciliation within the provider's documented deduplication window if supported and verified. Once outside a proven window, expose uncertain until an exact external receipt is recovered. A text match cannot establish receipt. Give the group sender the actual state and preserve the original group across rebind.
- Treat a permanently protected cleanup target as a known outcome. Blocking execution on hasPendingCleanup() would starve future input because protected targets currently count as pending. Block while a deletion owns admission and while a crash has left physical disposition unknown. Reconcile frozen targets before starting an execution that could use them. Release admission on a resolved protected or in-use outcome. Future deletion attempts must obtain exclusion and recheck usage again.
- TaskCloseout.remove writes released-resource:<task>:<resourceId>. acquireWorkspace currently derives the same resource ID and branch from repository name every time. For a released worktree, reserve a new acquisition generation in durable task/repository state before filesystem effects. Derive its resource ID, branch and workspace path from that generation. Retry an uncompleted acquisition with the same generation and reconcile the original worktree. Preserve generation zero for old resources and keep historical scopes and released markers. Every frozen old cleanup must remain unable to delete a newly acquired workspace. Recheck partially created worktrees after restart, including the gap between ensure, enrollWorktree and task.resources save.

## Caller usage

The names below are proposed. Each JSON argument object contains caller-supplied data only.

```text
send_agent_message({"requestId":"proof-1","toTaskId":"coordinator-task","text":"Verified release 71, see the attached run reference.","references":["run:71"]})
send_agent_message({"requestId":"check-2","toTaskId":"worker-task","text":"Please check the Linux result too."})
send_group_message({"requestId":"user-1","text":"The macOS run passed. The Linux run is still in progress."})
project_action({"action":"open_group","requestId":"discussion-1","taskId":"worker-task"})
project_action({"action":"schedule_reminder","requestId":"wait-1","dueAt":1837296060000,"text":"Check the Linux run."})
project_action({"action":"list_reminders"})
project_action({"action":"cancel_reminder","requestId":"cancel-1","reminderId":"wait-1"})
project_action({"action":"complete_task","requestId":"end-1","taskId":"worker-task","outcome":"delivered","summary":"Both runs passed","deliveryReferences":["run:71"]})
project_action({"action":"cleanup_artifacts","requestId":"clean-1","taskId":"worker-task","scopeIds":["owned-scope-id"]})
```

The group tool chooses the authenticated caller's current group. A Worker can open its own group or pass its known task ID. A coordinator can target one of its own Workers. A Worker learns its own and its coordinator's IDs in its dynamic context. The reminder creation request ID identifies a reminder within the caller's scope. Accept signed-safe epoch milliseconds within the supported Date range and reject an already expired new request. Resolve retries against their original persisted receipt before comparing the deadline to the current time.

## Types and persistence

```ts
type ProjectToolCall =
  | { tool: 'project_action', arguments: ProjectAction }
  | { tool: 'send_agent_message', arguments: AgentMessageArgs }
  | { tool: 'send_group_message', arguments: GroupMessageArgs }

type MessageDelivery =
  | { kind: 'agent', inputId: string, fromTaskId: string, toTaskId: string, status: Inbox['status'] }
  | { kind: 'group', outputId: string, fromTaskId: string, chatId: string, status: Outbox['status'] }

type Reminder =
  | { state: 'scheduled', dueAt: number, text: string }
  | { state: 'fired', dueAt: number, text: string, inputId: string, firedAt: number }
  | { state: 'cancelled', dueAt: number, text: string, cancelledAt: number }

ProjectRuntime.call(callerId, call, assertActive, identity)
Store.fireDueReminders(now) // one transaction per bounded batch, returns recipients to schedule
TaskCloseout.complete(input)
TaskCloseout.requestCleanup(input)
TaskCloseout.reopenOnInput(taskId, sequence)
TaskCloseout.reserve(taskId)
```

Derive argument types from strict Zod schemas. Map the native named tool and CLI argument name onto the internal discriminant. Keep the fallback's existing two-argument administrative invocation available for supported project actions, and expose named send invocations such as project-client CAPABILITY send_agent_message JSON_FILE. The fallback API may use one internal socket route with a discriminated envelope. A client on a retained Thread has both callable capabilities through shell even if Codex still displays an obsolete tool. Reject retired names in both paths and surface the new actual invocation in per-input instructions for retained active turns.

Use a composite unique key (owner_task_id, reminder_id) and an index on (state, due_at) in SQLite. Set exactly one terminal state with a conditional update of scheduled. In the same transaction as fired, insert its unique original-thread input with self-reminder provenance. Cancel changes only a still scheduled row. If firing wins, report fired together with actual input status. Normalize old retries against stored immutable identifiers. Paginate self-scoped listings. Scan on existing recovery and tick, including ticks racing recovery. An empty due index produces zero task inputs.

## Upgrade decisions

Apply synchronous, idempotent schema/ledger normalization before any Feishu receive callback, recovery cleanup, task sweep or new Codex tool request. Verify access via Store opened on a pre-upgrade database. Keep role identities, execution choices and their source, source revisions, task/Thread/group bindings, pause markers, retained records, native approval cards and input/output IDs.

- Legacy report receipts, intermediate group audits, delivered coordinator event inputs and worker_result events remain read-only and queryable. A pending old delivery row already in the inbox/outbox retains its original ID and normal recovery. For a result declaration look up its exact old worker-result event key, the forwarded-turn marker and related explicit report proof. Published records resolve to their original delivery and its live receipt. Suppressed/invalidated declarations retain their disposition. If an unpublished declaration has no prior accepted output, record “registered under previous contract, never submitted to recipient” as an explicit terminal migration disposition. A claimed publication with missing proof stays unresolved and visible. Uncertain existing receipt uses seenInputIds or exact Feishu evidence, and an upgrade never synthesizes a replay from a historical ordinary final. A query returns each outcome, including unresolved. Remove the live pending-result pointer from all execution decisions.
- Old current completion becomes one historical record with current completed state and the pre-upgrade inbox sequence. Preserve partial cleanup operations and frozen target evidence in history. Explicit old scope-cleanup operations retain their existing authorization and recovery. For implicit completion targets, preserve physically removed targets, identify untouched items as retained and release their seals when safe; if an old operation was interrupted after a rename or worktree removal, reconcile the actual frozen identities and expose partial retention/disposal. Finish any remaining destructive action only against a new explicit cleanup intent for that precise target. Never infer a cleanup operation solely from a historical lifecycle mark. Include a way to reselect a retained or interrupted old scope without discarding the original disposal identity. A pre-upgrade completed-followup already accepted to the coordinator retains its one original delivery.
- Historical coordinator decisions and Worker assignment text remain readable. Migrate generated Runtime scaffolding by matching exact known versions and boundaries. Any model- or user-written assignment that mixes task scope with obsolete tool directions is retained in history; project current instructions render the original goals and authorization with the narrow obsolete workflow directives superseded. Remove mechanically separable superseded directives from the rendered current context and identify custom project policies that need targeted edits. Keep genuine user restrictions (including investigation-only) in the live assignment even if an older Runtime also added a restriction. Check active-thread steer and idle-thread resume, including project-client refresh after the capability socket changes.
