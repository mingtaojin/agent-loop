# Agent Loop 项目协调者需求规格

日期：2026-11-12

本文记录本次讨论形成的项目协调者需求，作为设计与验收的依据。核心需求和项目授权已经用户逐项确认，少量边界建议单独列为待确认。用户随后明确要求使用 poteto-mode 根据本规格实现，当前状态为 `ready-for-agent`。该实现请求不自动要求切换正式服务或操作现有业务 Issue。

## 1. 目标

用户将一个项目交给长期协调者。协调者自动接手指定范围内的 GitHub Issue，组织调查、需求澄清、开发、验证、PR 合并和收尾，在需要业务决定或超出授权时通过项目群与用户沟通。

Agent Loop 增加协调者委派、监督和接收结果的能力。协调者使用 pstack Orchestrate，Worker 使用 poteto-mode 并自行选择适用的 playbook。Runtime 提供可靠执行和通信能力，不将各 playbook 的步骤重新编码为固定工作流。

长期协调者表示项目责任和记录持续存在，不要求单个模型会话永久运行或记住全部历史。

## 2. 确认范围与依据

本文使用三种标记区分需求依据。

| 标记 | 含义 |
| --- | --- |
| 已确认 | 用户在本次讨论中明确提出或接受的要求与授权 |
| 沿用 pstack | 用户已确认采用的工作方法，具体执行遵循适用的 skill 与 playbook |
| 待确认建议 | 讨论末尾提出但尚未逐项确认的边界处理，不得当作新增授权 |

本规格以对话中的最终决定为准。Freedom 上的 `C:\Users\jmtfr\Downloads\agent-loop-pstack-orchestrate-design.md` 是最初讨论资料，其组件、表名、API 和阶段划分不自动成为本规格要求。此前源码核实用于后续技术设计，不限制产品需求。

## 3. 角色与职责

本节说明本功能中的角色，不预先决定对应的数据库实体或 Thread 结构。

| 角色 | 职责 | 依据 |
| --- | --- | --- |
| 用户 | 确定项目目标、业务含义、重要取舍和授权；可直接指导具体任务 | 已确认 |
| 项目协调者 | 接手工作、组织委派、安排顺序、监督执行、核查产物、安排独立验证、推进交付与收尾 | 已确认、沿用 pstack |
| Worker | 使用 poteto-mode 完成被委派的调查、澄清、设计或开发，报告问题及成果 | 已确认 |
| PR Owner | 对一个 PR 负责，维护分支、处理反馈，并在条件满足后执行合并 | 沿用 pstack |
| 独立验证者 | 独立于代码作者，依据验收要求检查待交付代码与真实行为，提供证据和结论 | 沿用 pstack |
| Runtime | 提供任务委派、输入与结果传递、状态持久化、执行资源和恢复能力 | 已确认 |

协调者不亲自编写业务代码，不逐步指挥 Worker 如何复现、定位和测试。Worker 内部是否使用子 agent、使用哪些工程技能，由 poteto-mode 及具体任务决定。

PR Owner 是持续的责任，不要求由同一个执行会话永久承担。替换执行者时，按 pstack 保全上下文和成果，并维护同一分支只有一个有效写入负责人的约束。

## 4. 已确认的功能需求

### R01. 项目支持多个相关仓库

一个项目协调者统一负责多个相关仓库，例如前端、后端和插件仓库。跨仓库工作由同一个协调者对整体交付负责。

每个仓库可以分别设置 Issue 接手条件。不按仓库或技术栈预设常驻经理；子协调者按 Orchestrate 的适用条件引入。

### R02. 指定范围内的 Issue 自动接手

在项目指定的仓库范围内，Issue 满足以下任一条件即进入协调者的接手范围。

- 带有配置的指定标签。
- 被指派给配置的指定账号。

两类条件是“或”的关系，不要求同时满足。范围外的 Issue 不因被模型认为相关而自动接管。

首次启用时接手符合条件的存量未关闭 Issue，之后持续接手新进入范围的 Issue。对已有处理者或进行中的 PR，先核对实际进展，避免重复派单。

自动接手表示协调者开始对事项负责，不表示需求已经明确，也不表示额外授权已经成立。目标清楚的工作可以执行；信息不足时先调查；仍有业务歧义时向用户确认。

### R03. 协调者自主安排工作

工作安排遵循以下优先顺序。

1. 用户在项目群中明确指定的优先级。
2. 项目约定的 GitHub 优先级标记。
3. 协调者根据任务依赖、阻塞影响和可用执行资源作出的安排。

协调者不逐次请求用户确认执行顺序。独立任务可以并行，存在依赖或共享写入冲突时按 pstack 安排。

单个任务等待用户决定时，仅暂停受影响的工作，其他不受影响的任务继续推进。

### R04. 委派携带完整的任务约定

协调者向 Worker 交代目标、必要上下文、允许和禁止修改的范围、禁止动作、验收证据及交付要求，并明确使用 poteto-mode。

Worker 自行选择适用 playbook。Runtime 不根据 Issue 类型强制执行预置的调查、开发或合并阶段。

不同委派可以具有不同交付目标。需求尚不明确时，可以先委派调查和澄清，交付确认过的文档与验收条件，不要求此时已经具备完整开发任务。

开发在独立工作树和分支中进行，完成后提交 PR，由 Worker 承担 PR Owner 职责。纯调查或需求澄清任务按其约定交付文档和证据。协调者核查实际工作区和成果，不能仅凭派单文字认定已实现隔离。

### R05. Worker 主导具体需求澄清

具体需求不明确时，由负责该需求的 Worker 使用 poteto-mode 和 grill-with-docs。

Worker 先调查已有代码、资料和行为，确定能够自主查明的事实，再提出需要用户决定的问题。问题包含背景、选项、影响和建议。

协调者将问题带到项目群，必要时补充项目已有决定和跨任务影响。用户回答后，原 Worker 接收答复，更新需求文档并继续澄清。协调者不重复开展另一套针对同一需求的 grill。

需求与必要的架构取舍确认后，形成可交付的验收条件，由协调者按已有授权安排开发。是否沿用原执行者，遵循 pstack 的委派和交接规则。

项目级优先级、项目范围等问题由协调者直接与用户确认。

### R06. 技术工作自主推进，业务取舍升级给用户

预期行为已经明确的技术问题，由 Worker 自主调查、修复和验证。

需要用户决定的事项包括业务含义仍不明确、公共契约变化，以及明显扩大原任务范围的重要取舍。协调者携带调查证据、备选方案和影响向用户提问。

Worker 或协调者的推测不得记录为用户已确认的决定。用户对单个任务的答复不得自动扩大为整个项目的授权。

### R07. 项目群是主要交流入口

用户主要在项目群与协调者沟通。协调者汇总 Worker 的业务问题、保留来源和上下文，并将用户决定送回相关任务。

Worker 的任务群保留。用户可以查看或直接指导具体任务。直接指导中影响项目或其他任务的决定，应能被协调者获知，以免不同任务沿用冲突结论。

业务决定与具体工具的原生审批保持区分。统一交流入口不能把普通答复变成工具批准。

### R08. Issue 新评论先交协调者判断影响

已接手 Issue 出现新评论时，协调者先接收评论及来源，结合当前目标、进展和已有决定判断影响，再按需将内容交给负责该 Issue 的原 Worker。

不因新增评论重复创建任务或重置调查成果。该规则不限制 pstack 在执行者失效时进行必要替换。

| 评论类型 | 要求 |
| --- | --- |
| 日志、复现步骤、环境补充 | 作为新证据交给原 Worker 核查 |
| 修复无效或遗漏场景 | 核查原因，必要时修改代码并补充验证 |
| 原需求澄清 | 核对是否与已确认决定一致，有冲突时向用户确认 |
| 新增需求 | 判断是否超出原任务范围，明显扩大范围时交用户决定 |
| 进展询问 | 根据核实过的状态答复，不重复开展工作 |
| 跳过检查、立即合并或部署的要求 | 不将评论自动解释为额外权限批准 |

可能影响正确性或验收目标的评论，在核查清楚前暂缓相关合并。合并后发现的问题按后续修复处理，保留原交付记录。

后续信息以可追溯的补充或修订进入任务，不能静默覆盖原任务目标、已确认决定或授权。

### R09. 监督依据真实产物

协调者检查实际 diff、产物、PR 状态和验收证据，不仅接受 Worker 的文字汇报。运行状态、工作成果、验收结论和最终交付分别表达。

一轮模型执行结束不自动表示工作完成，Worker 提交 PR 不自动表示通过验收。协调者依据 Orchestrate 跟进所有已派出的工作，包括完成、替换或范围被接管的情况。

Worker 停滞、失败、越界或反复循环时，按 pstack 调整范围、恢复、替换或重新规划。不能通过无限重试或放宽验收条件掩盖问题。

### R10. 验证通过后自动合并

项目具有以下常设授权，无需逐个 PR 再征求用户同意。

- 当前待合入代码获得独立于作者的有效验证结论。
- 满足仓库检查、分支保护和适用的 pstack 合并要求。
- 没有尚未解决、影响本次交付的业务决定。
- 用户没有要求该 PR 暂缓或由其亲自审核。

条件满足后，由协调者安排 PR Owner 合并。不得绕过仓库保护要求，不得将部署纳入这项授权。

验证证据必须覆盖实际合入的代码及相关基线。代码或基线变化时，依据适用 playbook 判断需重新验证的部分，不能默认沿用旧结论。CI 通过不能替代独立的行为验证。

协调者确认 PR 已实际合并。进入合并队列、开启自动合并或命令已提交，不能单独作为完成事实。

### R11. 目标全部满足后自动关闭 Issue

协调者确认 Issue 的完整验收目标满足、相关 PR 已实际合并后，可以自动关闭 Issue，并留下交付说明和验证证据链接。

一个 Issue 对应多个 PR 时，必须等完整目标满足。仅完成部分工作不得提前关闭 Issue。

### R12. 安全清理任务拥有的临时资源

本条由 [Task 收尾规格](../task-resource-cleanup/spec.md) 和 ADR 0014 更新。正式结束通过协调者的 complete_task 提交。临时文件、构建产物、已交付的证据副本，以及已交付、被替代或明确放弃的未提交和未合并工作可以释放。数据库保留摘要、决定、交付引用及清理回执。

唯一未交付成果、其他任务仍在使用的资源和无法核对身份的路径继续受保护。普通 release_workspace 保持未提交和未合并保护，不继承正式收尾的弃置授权。

清理范围不扩展到原始工程目录或其他任务的资源。清理完成与 PR 合并分别核实，不能因为 PR 已合并就认定清理已经成功。

### R13. 项目责任独立于单个会话

项目规则、授权、已确认决定、任务关系、负责人、阻塞、待决问题和下一步行动，需要持久保存并可追溯。

Worker 保留具体任务的详细过程。协调者接收必要报告，按需检查原始证据，不要求把全部 Worker 对话和日志长期装入自己的上下文。

协调者上下文过长或会话失效时，可以更换会话继续负责原项目。恢复后核对当前任务、PR 和验证的真实状态，继续处理尚未处理的信息。

恢复不得导致重复派单、遗漏待决问题、重复询问已经确认的事项，或把过期验证结论当作当前有效结论。

决定被修改时，保留修改记录并明确当前有效内容。长期项目身份不绑定单个 Codex Thread。

### R14. Runtime 提供通用协调能力

Runtime 必须支持协调者完成以下行为，具体工具形式留待设计。

- 委派独立任务，并保留委派方、执行方和相关任务的关系。
- 向已委派任务补充信息、传递用户决定和调整后的工作说明。
- 接收 Worker 的问题、成果和执行状态，使协调者能够继续处理。
- 查询任务及相关成果，供协调者核查和安排下一步。
- 在重启、重复消息和会话替换后保持关系与投递记录，避免重复执行。

信息来源与授权身份必须保留。Worker 报告、Issue 评论和用户决定不能互相冒充。

以上是产品能力要求，不规定工具名称、数据库表、消息协议或固定任务阶段。

## 5. pstack 的使用边界

下表是工作方法的对应关系，不是 Runtime 必须执行的阶段表。

| 工作 | 适用 skill 或 playbook | 使用者 |
| --- | --- | --- |
| 项目组织、委派、监督和重新规划 | Orchestrate | 协调者 |
| 具体任务内的方法选择 | poteto-mode | Worker |
| 模糊需求澄清与文档记录 | grill-with-docs 及其依赖 | 需求 Worker |
| 缺陷复现、根因定位、修复和验证 | Bug fix | Bug Worker |
| 功能设计与开发 | Feature | 开发 Worker |
| PR 审核意见与 CI 跟进 | Babysit | PR Owner 或其安排的执行者 |
| 独立验证与合并 | Shipping，独立队列在适用时使用 Autopilot-full | 协调者、独立验证者和 PR Owner |
| 临时工作区清理 | Worktree cleanup | 协调者安排的执行者 |

一个 PR 同时只有一个写入负责人。每个 PR 的验证者独立于作者，模型选择遵循 pstack 的适用配置。先验证一个工作单元的完整交付链，再扩大并行范围。

pstack 中依赖特定宿主的工具和执行机制，需要映射到 Agent Loop 可用能力。映射不得改变项目授权或伪称尚未具备的工具已经可用。

本规格不复制整套 playbook，也不固定模型、并发数、重试次数或轮询间隔。设计与实现阶段需记录采用的 pstack 版本或快照，以便复核所依据的规则。

## 6. 角色指导与任务说明

协调者需要明确获得 Orchestrate 职责，Worker 需要明确获得 poteto-mode 指导和本次任务约定。后续评论与决定需要保留变化记录。

讨论中提出的“公共约束、角色指导、具体任务说明”三层组织方式是设计候选，不是已经选定的实现结构。

| 内容 | 需要表达的信息 |
| --- | --- |
| 公共约束 | 用户授权、项目说明、证据要求与来源边界 |
| 协调者指导 | 项目责任、Orchestrate、委派与监督、独立验证、用户交流入口 |
| Worker 指导 | poteto-mode、具体任务责任、反馈与交付约定 |
| 本次委派说明 | 目标、上下文、工作范围、禁止动作、验收条件和交付要求 |

项目的仓库范围、接手条件和授权属于项目约定，不应依赖每个 Worker 自己猜测。独立验证任务要明确待验证的产物、版本、验收条件和允许操作。

## 7. 验收场景

以下场景描述外部可观察结果，不限定实现。此处是未来验收要求，不是已经通过的测试记录。

| 编号 | 场景 | 预期结果 | 关联要求 |
| --- | --- | --- | --- |
| A01 | 指定仓库的三个 Issue 分别只满足标签、只满足指派、两者都不满足 | 前两个被接手，第三个不被自动接管；同时满足两项也只接手一次 | R02 |
| A02 | 首次启用时已有符合条件的未关闭 Issue，其中一个已有处理者和 PR | 接手存量事项，核对已有工作，不重复开工 | R02 |
| A03 | 多个任务具有用户指定优先级、项目优先级和依赖关系 | 按既定规则安排，独立任务可并行，不逐次请求排序批准 | R03 |
| A04 | 技术 Bug 的预期行为明确 | Worker 使用 poteto-mode，在独立工作树修复并提交 PR，协调者核查产物 | R04、R06、R09 |
| A05 | 需求只有“支持批量导出” | Worker 调查后用 grill-with-docs 提问，用户在项目群答复，决定进入需求文档；明确后再安排开发 | R05、R07 |
| A06 | 一个 Worker 等待业务决定，另一个任务不受该决定影响 | 前者等待，后者继续推进 | R03、R06 |
| A07 | 开发中的 Issue 收到新增日志和复现条件 | 协调者判断影响，原 Worker 接收信息并继续，不创建重复任务 | R08 |
| A08 | 评论要求增加明显超出原范围的功能，或要求跳过验证部署 | 范围变化交用户决定，评论不成为额外授权 | R06、R08、R10 |
| A09 | PR 已准备合并，新评论提供可能影响正确性的证据 | 暂缓相关合并，核查后按 pstack 决定后续处理 | R08、R10 |
| A10 | 作者汇报测试通过，但独立验证失败 | 不合并，Owner 处理问题，并提供覆盖更新代码的验证证据 | R09、R10 |
| A11 | 验证后代码或相关主干发生变化 | 核对证据有效性，完成适用检查后才能合并 | R10 |
| A12 | PR 满足全部门槛，且没有用户保留的审核要求 | 无需再次确认即可安排合并，并核实最终合并状态 | R10 |
| A13 | 用户要求亲自审核某个 PR | 该 PR 等待用户决定，不被常设自动合并授权覆盖 | R10 |
| A14 | 一个跨前后端 Issue 需要多个 PR，其中只合并了一部分 | 由同一协调者跟进整体交付，Issue 保持打开；全部满足后再自动关闭并留存证据 | R01、R11 |
| A15 | 合并后有可清理工作树、未提交成果和仍被其他任务使用的工作树 | 只清理符合条件的任务资源，保留其余资源并说明原因 | R12 |
| A16 | 用户在 Worker 群直接修改一个影响其他任务的业务决定 | 协调者能够获知决定及范围，相关任务不继续沿用冲突结论 | R07、R13 |
| A17 | 多个 Worker 正在运行，一个等待用户答复，此时协调者更换会话 | 恢复负责人、待决问题、授权和下一步，核对最新状态，接住后续结果，不重复派单或重新提问 | R13、R14 |
| A18 | 委派或结果消息重复到达，或投递期间发生重启 | 保留关系与投递结果，不创建重复执行，不把未知结果当作成功 | R14 |
| A19 | Worker 正常结束一轮，但只交付了调查报告 | 协调者按原委派目标判断成果，不将轮次结束直接解释为 Issue 已完成 | R04、R09 |

设计验收还需确认 Runtime 没有固定编码 Bug fix、Feature、grill 或 Shipping 的工程步骤。平台替身测试、真实 Agent 行为验收、真实 GitHub 与飞书联调分别提供证据，不互相替代。

## 8. 待确认的边界建议

以下建议尚未获得逐项确认。相关设计需要采用这些行为时，再确认所涉及的业务语义，不重新询问已经明确的授权。

| 编号 | 场景 | 建议处理 | 尚需明确的边界 |
| --- | --- | --- | --- |
| O01 | 已接手 Issue 被移除标签或改派 | 不自动丢弃正在进行的工作，由协调者核查变化含义 | 脱离接手范围后是否继续负责，以及何时交还 |
| O02 | 用户要求暂停整个项目 | 停止新派单，通知相关 Worker 安全停止并保留现场 | 项目暂停的覆盖范围，以及已进入外部合并队列的处理方式 |

Worker 故障恢复、替换和验证受阻，优先遵循 pstack 与已确认的授权边界。实现不能把这些技术问题转成无意义的重复授权请求。

## 9. 留待设计的技术选择

以下问题由设计与验证解决，不作为额外的用户需求选择题。

- 协调者是否复用 Task，以及角色和项目关系如何表达。
- 委派、任务通信、结果提交与查询采用何种工具或接口。
- 如何保证幂等、事件持久化、投递核对和有效写入者的唯一性。
- 协调者运行中收到事件时，如何安排追加、排队和后续处理。
- 项目记录、需求文档、决定与证据如何保存、索引和加载。
- 角色指导与任务说明如何组合，以及旧会话如何获取适用能力。
- 工作区归属、占用、释放与会话恢复如何配合。
- 如何将现有普通任务纳入协调，同时避免重复执行并保留其上下文。

设计不得为了适配当前实现而缩减已确认需求。任何会改变用户可见行为或授权的取舍，应明确提出。

## 10. 非目标

- 跨 Issue 自动识别共同根因、据此合并修复任务的额外规则。本轮已明确暂不加入。单个 Bug 的根因定位仍遵循 Bug fix。
- 将 pstack playbook 复制为 Runtime 的固定阶段状态机。
- 从一开始建立常驻前端经理、后端经理或每仓库经理。
- 默认部署、绕过分支保护或清理不属于任务的资源。
- 要求单个协调者 Thread 永久保存全部项目历史。
- 在本规格中确定数据库表、API 名称、模型配置或实现任务拆分。
