# 从父目录发现任务所需工程

Status: ready-for-agent

Implementation: complete locally. Automated checks and isolated real-Codex acceptance passed. The local service has been restarted, and existing task identities were verified.

## Problem Statement

飞书与 GitHub Issue 发起的任务需要先定位工程入口。当前用户必须逐个配置本地工程，执行代理才能从登记清单中选择。增加工程、移动工程或更换机器时，用户都要维护这些映射。

现有配置还将 GitHub 采集仓库与本地工程入口绑定在一起。用户只想指定工程所在的父目录，让执行代理依据任务材料找到对应工程，同时继续独立控制要采集哪些 GitHub Issue。

## Solution

用户配置一个工程发现根目录。系统发现该父目录的一级子目录，将其作为可选择的项目目录，临时选择会话依据任务材料判断需要哪个工程入口。

例如，`opentest` 和 `agent-loop` 是两个工程入口。`opentest` 内部的仓库、模块和版本由正式 Agent 根据任务继续定位，不作为独立工程入口。项目目录自身可以没有 Git 仓库，也可以包含多个独立仓库。

选择结果经 Runtime 校验、工程资源准备完成后，正式任务在选中的项目目录中开始。无需工程目录的讨论、目录不明确时的追问和已有会话恢复沿用现有行为。

工程发现根目录从配置读取。更换父目录只需修改配置。GitHub 采集仍由明确的仓库和收集条件控制，本地工程的发现不会自动扩大采集范围。

## User Stories

1. 作为配置维护者，我希望只配置一个工程发现根目录，以便免去逐个登记本地工程的维护。
2. 作为配置维护者，我希望工程发现根目录可以修改，以便移动工程后只需更新配置。
3. 作为在不同机器上运行 Agent Loop 的用户，我希望代码和默认值不包含本机固定路径，以便各自使用自己的工程目录。
4. 作为任务发起者，我希望父目录的一级子目录自动成为工程入口，以便直接使用已有工程布局。
5. 作为任务发起者，我希望新增的一级工程目录能在后续任务选择时被发现，以便不必再添加一条工程配置。
6. 作为任务发起者，我希望不存在的子目录不再作为新任务的可用入口，以便避免选择已经移走的工程。
7. 作为 OpenTest 用户，我希望选择的是完整的 `opentest` 项目目录，以便同一任务可以使用其中相关的仓库和资料。
8. 作为 Agent Loop 用户，我希望 `agent-loop` 与 `opentest` 在同一层被识别，以便不同工程按一致的规则选择。
9. 作为拥有多个工程的用户，我希望工程内部的仓库和版本不提升为独立入口，以便保持约定的工程边界。
10. 作为拥有多仓库工程的用户，我希望项目目录自身无需是 Git 仓库，以便使用包含多个仓库的完整工程。
11. 作为拥有资料目录的用户，我希望工程入口无需 Git remote，以便目录发现不依赖远端仓库信息。
12. 作为飞书任务发起者，我希望执行代理依据任务内容自行定位工程，以便交办任务时无需先维护工程映射。
13. 作为 GitHub Issue 任务发起者，我希望执行代理从同一批本地工程入口中选择，以便任务来源不限制工程发现能力。
14. 作为任务发起者，我希望原始任务、附件和已提供的目录答复都能辅助选择，以便执行代理拥有完整的定位依据。
15. 作为任务发起者，我希望执行代理可以只读检查候选工程来区分用途，以便不必完全依赖目录名字判断。
16. 作为任务发起者，我希望工程明确时直接完成选择，以便不必为每项任务重复确认目录。
17. 作为任务发起者，我希望工程无法确定时收到目录问题，以便补充信息后继续原任务。
18. 作为讨论任务发起者，我希望无需工程目录时可以直接讨论，以便普通交流不被工程定位阻塞。
19. 作为任务发起者，我希望目录选择阶段只处理入口判断，以便工程调查和实现仍在正式任务中开展。
20. 作为任务发起者，我希望正式会话在选定项目目录中运行，以便实际文件操作与选中的工程一致。
21. 作为任务发起者，我希望正式 Agent 继续定位工程内部所需的仓库和版本，以便入口选择保持在已约定的层级。
22. 作为任务发起者，我希望临时选择会话与正式会话相互独立，以便正式任务保留清晰的持续上下文。
23. 作为任务发起者，我希望目录答复中的操作限制进入正式任务，以便诸如只排查、不改代码的要求在执行前可见。
24. 作为任务发起者，我希望目录答复中的附件保持内容和顺序，以便工程工作不会缺少我补充的证据。
25. 作为任务发起者，我希望临时选择问题和推理不复制到正式会话，以便正式任务接收原始要求和必要的环境信息。
26. 作为 GitHub 采集配置维护者，我希望继续明确配置采集仓库和条件，以便自行控制哪些 Issue 成为任务来源。
27. 作为 GitHub 采集配置维护者，我希望增加本地工程不会自动采集新的远端 Issue，以便本地目录变化不改变收集范围。
28. 作为只通过飞书使用本地工程的用户，我希望定位工程无需配置对应的 GitHub 来源，以便本地工程与任务采集分别维护。
29. 作为配置维护者，我希望 GitHub 来源配置不再要求为发现根目录下的每个工程维护本地入口映射，以便一个父目录足以承担工程发现。
30. 作为已有任务的用户，我希望修改发现根目录不改变已有正式会话及工程资源，以便继续原来的工作。
31. 作为服务重启后的用户，我希望恢复已保存的工程选择和资源，以便不因重新发现目录而切换工程。
32. 作为等待目录答复的用户，我希望重启后仍能回答原问题并继续任务，以便保留已有对话与附件。
33. 作为已有工程资源的用户，我希望原共享目录与独立工作目录的关联仍能恢复，以便兼容先前任务。
34. 作为任务发起者，我希望保存的工程目录失效时明确报告问题，以便处理现场而不是被自动切换到其他工程。
35. 作为工程所有者，我希望目录选择不会新建分支、改动工程文件或覆盖已有修改，以便保护正在进行的工作。
36. 作为工程所有者，我希望发现工程不会扩大修改、部署或原生工具授权，以便延续现有操作边界。
37. 作为任务发起者，我希望模型选择经过候选入口校验，以便任意返回的目录不能直接成为执行环境。
38. 作为验收者，我希望实际运行的正式进程能证明自己的工作目录，以便验证工程发现最终影响了执行环境。

## Implementation Decisions

- 配置模块提供单个工程发现根目录配置项。路径解析遵循现有配置的相对路径约定，不设置与本机用户目录绑定的默认值。
- 工程发现模块枚举该根目录的一级工程目录。开始一次新的工程入口选择时获取当前候选，不要求额外登记目录名、仓库名、分支或 Git remote。
- 工程入口保持在一级子目录层级。允许读取工程内资料辅助定位，但不递归生成内部仓库或版本入口。
- 项目目录沿用共享工程目录的语义，可以没有 Git 元数据。发现与准备入口本身不创建任务分支或 Git worktree。
- GitHub 采集配置与本地工程发现分别承担职责。Issue 的来源身份及收集条件继续保留，不能将发现的本地目录自动转换成 GitHub 采集仓库。
- 任务编排模块为飞书与 GitHub Issue 新任务提供相同的工程候选。Runtime 提供候选与校验，工程用途和匹配关系由临时模型依据任务材料判断。
- 临时选择会话沿用只读、无动态工具和独立进程释放规则。允许为区分候选而读取必要资料，禁止在该阶段执行任务中的调查、实现、部署或工程技能。
- 选择请求和结构化结果能够引用发现的项目目录。选中工程不再要求伪造 GitHub 仓库身份、基准分支或逐个注册的仓库配置。
- Runtime 按本次候选校验选择结果，在创建正式会话前验证项目目录，保存工程选择与工程资源关联。不能将模型任意返回的名称或路径直接用作工作目录。
- 工程资源与持久化模型区分工程入口身份和 GitHub 来源身份，保存恢复任务所需的目录与资源信息，兼容已有共享项目目录和独立 Git 工作目录记录。
- 正式会话以资源管理器确认的项目目录为实际工作目录，读取该工程说明。内部仓库、版本及其工作方式由正式 Agent 按任务需要确定。
- 目录问题、无需工程目录和用户补充的处理规则保持。用户的目录答复与附件进入正式任务，临时会话的模型历史不进入正式任务。
- 已建立的正式会话不重新选择目录。配置修改或发现结果变化不自动重绑已有资源，恢复仍验证已保存关联。目录丢失、类型错误或关联改变沿用现有报错与保留现场行为。
- 正式任务按需申请其他工程资源的既有能力保持。相关入口复用同一套工程身份、校验与持久化规则，继续恢复原有资源关联。
- 未建立正式会话的任务按现有选择恢复规则继续。配置与候选读取变化不得破坏用户答复、附件顺序、输入投递去重和未知回执处理。
- 配置诊断、使用说明和示例随功能更新，说明父目录配置、一级入口规则、GitHub 采集边界及原有任务的恢复行为。

## Testing Decisions

- 主要测试边界使用现有 `AgentLoop` 的公开任务入口与恢复入口。通过飞书消息接收、GitHub 收集、任务推进及恢复观察完整行为，不为目录枚举另开一套面向测试的公开接口。
- 复用现有工程选择测试夹具中的真实临时目录、持久化存储和 `WorkspaceProvider`。自动化测试替代外部飞书、GitHub 和 Codex 服务，检查最终任务状态、资源关联、正式会话请求及投递内容。
- 测试断言用户可观察的结果，不绑定内部函数划分、目录遍历算法、固定序列化布局、模型推理文字或提示词全文。依赖调用次数的断言仅用于验证重复选择、重复建会话或重复投递等行为。
- 在两个隔离的临时父目录中创建不同工程，分别加载配置并发起任务。验证候选和新正式会话工作目录随配置变化，证明实现不依赖本机路径。
- 在同一父目录下创建无 Git 元数据的多仓库工程、另一个普通工程及嵌套版本目录。验证只有一级项目目录成为入口，内部资料仍可供选择和正式任务使用。
- 覆盖增加、移走工程后的新任务选择。候选变化不能将已有正式任务迁移到新目录。
- 分别从飞书消息与 GitHub Issue 入口发起任务。验证两者都能选中未逐项登记的本地工程，并创建工作目录正确的正式会话。
- 检查 GitHub 采集仍只针对配置的来源和收集条件。增加工程目录不能增加远端采集范围，本地工程没有对应 GitHub 配置也不影响选择。
- 覆盖临时模型返回有效候选、候选之外的选择、无需工程目录和目录问题。无效选择不得准备资源或创建正式会话。
- 延续现有工程选择回归案例，覆盖原始材料、目录答复、操作限制及附件完整投递，以及来源更新不能冒充目录答复。
- 延续已有恢复测试，覆盖等待答复时重启、已选目录时重启、已有正式会话、旧工程资源以及选择期间到达的新输入。选择与投递回执未知时不盲目重复执行。
- 沿用共享项目目录的既有测试，验证读取完整工程、保护已有修改、不创建分支，以及目录丢失、文件冒充目录和符号链接改指向时拒绝错误恢复。
- 配置边界测试仅补充现有最高层流程难以定位的输入错误，复用配置加载的既有案例，验证根目录解析和无效配置反馈。
- 真实验收沿用已有真实 Codex、临时工程与合成平台输入的工程选择验证方式。将候选改为仅由父目录发现，至少完成一次自动定位和一次目录答复后定位。
- 真实验收检查临时与正式 Thread 不同、目录答复在首轮可见，并让正式进程在目标夹具中生成包含实际工作目录与任务标记的结果。读取产物核实目录和输入，不能只以模拟的会话创建参数判定验收通过。
- 自动化测试、真实 Codex 验收与生产配置更新分别记录结果。现有真实验收使用合成平台，不能据此声称已完成真实飞书或 GitHub 平台验收。

## Out of Scope

- 从本地 Git remote 自动发现 GitHub 采集仓库，或改变已有 Issue 收集条件。
- 将工程内部的仓库、模块或版本递归提升为独立入口。
- 同时配置多个工程发现根目录，或构建工程标签、别名及人工描述管理系统。
- 自动 clone 仓库、创建缺失工程、移动工程或修复失效目录。
- 重新选择或迁移已有正式会话的工程目录，自动覆盖已有工程资源关联。
- 为共享项目目录增加跨任务文件隔离，或替正式 Agent 决定工程内部的分支、worktree 和交付策略。
- 更换选择模型、改变正式任务模型、放宽临时选择权限或新增业务开发阶段编排。
- 文件系统实时监听和配置热加载。目录发现只需在正常加载配置后为新任务反映当前工程；无需承诺后台持续监听。
- 由本规格发布动作修改运行代码、更新实际运行配置、重启服务、部署或执行真实工程任务。
