# 按需任务群

项目协调群是日常交流入口。Worker 和 verifier 创建、运行、提问和交付都不要求有任务群。用户向协调者提出直接对话需要后，协调者识别本项目任务并调用：

```json
{"action":"open_group","requestId":"stable-open-id","taskId":"target-worker-id"}
```

同一请求重试返回原回执。不同请求打开同一有效群也不会新建群。群已失效时，需要新的开群请求。只有协调者能打开本项目 Worker 或 verifier 的群，不能借此管理其他项目的任务。普通问题经 `send` 转交；原生审批自动开群，仍只接受实际用户的认证按钮操作。

无群期间的普通飞书输出标为 `dropped`，原文和执行事件仍保存在本地，协调者仍收到任务事件。开群只显示欢迎、状态和最近的最终摘要，不补发旧输出。无群任务的 dashboard 标题继续来自原始任务来源，群名修改不参与任务标题或搜索。

群被解散、ID 无效或不再满足任务群的所有者与私密性要求时，解除群关联并保留 Thread、状态、输入和待审批。权限或网络错误不是已解散的证据。群重建增加代次，群标记、创建 UUID、审批输出和进度资源不会误用旧群身份。任务群不会自动解散。

普通消息的未知发送结果不自动重发。仍有效的原生审批卡可在未知结果后重试，间隔至少 30 秒，沿用同一消息 UUID。在飞书 UUID 去重窗口之外可能出现第二张相同请求卡，但实际批准仍绑定同一个原生请求，原生决策队列只接受一次，不重复工具执行。旧群卡或过期请求不能批准新请求。

## 清理既有任务群

执行前需要独立的用户授权和已经生效的本版 Runtime。API 解散会永久删除飞书聊天记录。禁止先在旧版服务上解散运行任务的群。

1. 协调者调用 `plan_group_cleanup`，携带稳定 `requestId`。返回的计划冻结全部当前任务群，排除所有项目协调群，并在项目群展示一次。计划之后新建的群不加入旧清单。
2. 用户核对清单后，发送其中的精确确认文本。协调者调用 `confirm_group_cleanup`，携带 `planId` 和该消息的 `messageId`。代理转述、原生工具批准以及计划前的泛化授权都不能代替此确认。
3. 协调者调用 `apply_group_cleanup`，携带 `planId` 和新的稳定 `requestId`。计划逐项保存尝试、成功、已不存在、跳过、失败或未知结果。任一错误停止本批，包括权限错误。已失效的旧绑定不会指向后来重建的新群。
4. 修复阻塞后，使用新的 apply 请求继续同一个计划。同一 apply 请求只返回原回执，不重复执行。结果未知的项先检查远端群状态；已解散直接完成，仍存在才继续删除。已成功项不再删除。

需要 `im:chat:delete` 或更宽的 `im:chat`。机器人不是群主时，还必须是群创建者并具有 `im:chat:operate_as_owner`。官方说明见[解散群](https://open.feishu.cn/document/server-docs/group/chat/delete)。`232009` 表示已解散，`232006` 表示 ID 无效；后者不会作为已成功删除处理。所有计划和逐项结果保存在本地持久记录中。

## 与 coordinator-only intake 的组合

本变更基于 main 的项目成员机制。未加入项目的独立任务保留既有入口，不复制 coordinator-only intake 的来源选择和晋升逻辑。

与 PR17 合入时，保留其 `purpose` 和 `advanceUnassigned`、私聊回复、GitHub intake 与 CLI 回执逻辑。`setup` 中项目成员不再一律调用 `ensureGroup`，只有 coordinator 默认开群，其余通过 `TaskGroups.open`。intake 不进入执行 setup，必须保持无群。私聊、GitHub 和 CLI 的后续问题由其协调者入口回答；晋升为 Worker 后也不自动建群。保留本变更的原生审批、失效群恢复和输出策略。

进度总览、群名变更同步和初始群名摘要不在本次变更内。真实群写入验收、部署和既有群清理需要各自授权；离线行为测试不能代替这些操作的真实验收。
