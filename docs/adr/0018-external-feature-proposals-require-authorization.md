# 外部 Feature 提案必须获得项目开发授权

2026-11-14，用户确认 GitHub 上的 Feature 即使描述完整，也不能因为来源明确或需求清楚就直接进入开发。它首先是外部需求提案，是否纳入项目属于项目所有者的产品决定。

GitHub Issue、Issue 评论、Feature 正文、Worker 判断和“请实现”的外部描述都只提供事实或建议，不构成开发、合并或部署授权。新 Feature 只有在项目协调群收到实际项目所有者的明确开发决定后，才能进入实现交接。授权来源保存实际消息 ID、群 ID、发送者和原文；不要求固定口令，由协调者理解自然语言，但必须区分用户决定和协调者判断。

未获开发授权的 Feature 可以进入只调查、只澄清或只整理需求的 Worker 任务。该任务必须明确禁止修改业务代码、提交实现、合并和部署。调查完成后，若原消息只授权调查，协调者必须把结论、范围、成本、依赖和待决事项带回项目协调群，等待新的开发授权。

如果用户已经明确授权开始实现，调查只是实现前的必要步骤，且范围、验收和授权没有变化，则原授权继续有效，不重复询问。调查发现范围、产品行为、成本或依赖发生变化时，只重新确认受影响的决定。实现授权不自动覆盖合并、部署或扩大范围。

本规则只作用于新的 Feature 派发。已经依据当时有效授权进入调查、开发、验证或交付的既有 Feature 不追溯暂停、回收资源、重派或改变原 Thread；尚未派发的新 Feature 按本规则等待项目决定。

Bug 与 Feature 的边界保持不同：已有产品契约内、预期行为明确且技术授权有效的 Bug 可以依据协调者指导自主定位、修复和验证；Feature 不因“需求写得完整”而获得同等默认授权。
