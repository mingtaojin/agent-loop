探针实际确认以下行为。

1. 指定标签、指定账号和同时满足两项的 Issue 被纳入，范围外的 Issue 不被纳入。
2. 协调者调用 `project_action` 委派一个独立 Worker。
3. Worker 在协调者结束原轮次后读取夹具并报告唯一标记。
4. 报告唤醒原协调 Thread 的新轮次，并保留 Worker 来源。
5. 协调者通过 CAS 将结果写入项目记录。
6. 重启后 Task、Thread、项目关系和记录保持一致，没有新增重复 Worker。
7. 原始夹具文件未被修改，Runtime、App Server 与临时能力均完成清理。

其他正常时限探针也已通过。一次缩短时限的探针因等待模型结果超时记为 BLOCKED，没有计作通过。

## 独立审查与修复

独立只读审查发现并修复了三个问题。

- 普通仓库的服务端过滤会漏掉符合项目接手条件的 Issue。现在项目采集使用独立的无指派及标签前置过滤条件。
- 旧普通任务即使不匹配项目条件也会被接管。现在先检查项目接手条件，范围外任务继续原路由。
- Worker 群消息入库与协调者通知之间存在崩溃窗口。现在两者在同一事务中提交，重复投递也能修复旧通知缺口。

针对上述路径的独立静态复核给出 VERIFIED，相关回归测试通过。首次动态文件审查因并发编辑停止，后续广泛快照审查在形成发现后达到时限；没有将未完成审查报告为全量通过。最终复核针对已证明的问题进行。

工作区释放另补充了故障恢复验证：实际删除后丢失确认时，重启核对并完成释放记录，不重建已删除目录。

## 验证边界

本轮没有向真实飞书群或业务 GitHub 仓库发送验收消息，没有执行实际业务 PR 的审核、合并或 Issue 关闭，也没有切换正式服务。自动交付的项目授权已写入角色指导，但不能把本轮委派探针当作完整业务交付验收。

会话轮换、原生问题转接及角色模型恢复有 Runtime 和协议测试，未分别进行真实平台端到端验收。必要实机验证受阻时仍不得算作通过。

Runtime 工作树释放采用保守的提交保全检查。配置基线未更新，或 squash 合并不能通过祖先核对时，保留资源并报告原因。Worker 自建工作树按 pstack 的清理规则处理。
