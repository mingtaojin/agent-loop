# 共享需求工作流验证

本变更把各项目协调者与 Worker 的需求交接约定写入公共角色提示词。项目决定和授权继续通过现有项目记录保存。Runtime、数据库结构、全局技能、部署和真实任务状态不在本次变更范围。

## 场景核对

下表是对两个角色提示词的静态审阅。它描述应有的去向，不是实际模型已经执行这些场景的证明。

| 输入与已有约定 | 协调者与 Worker 的正确去向 | 需要核对的证据 |
| --- | --- | --- |
| 用户提出模糊想法 | 只委派调查和澄清，Worker 用 grill-with-docs 查事实、整理文档和问题，经协调者回项目群 | 未决问题、选项、影响、建议和真实用户答复来源；不实施业务代码 |
| 用户明确交办技术 Bug，范围与授权清楚 | 自主定位、修复和验证，不强制产品访谈或再求授权 | 原始 Bug 或 Issue、验收约定、已有有效授权 |
| 用户要求只讨论、不实现，即使所有问题已答完 | 继续调查和记录，直到用户改变限制 | 持续有效的讨论限制及后续实际用户输入 |
| 用户已确认需求文档并授权该范围开发 | 原 Worker 按可核对版本实施，再由非作者独立验证和按项目授权交付 | 文档版本、确认范围、不做范围、验收、未决事项及开发授权来源 |
| 用户要求少发消息 | 减少例行进度消息，仍提出必要决策并核对文档与授权 | 将沟通偏好与产品决定、开发授权分别记录 |
| 新评论改变需求或公共契约 | 协调者先评估差异和影响，只澄清受影响的事项，再 send 回原 Worker | 原版本、新输入来源、改变与未改变的范围；不静默扩大 |
| 新建、恢复或更换协调会话 | 读取 status 与相关持久记录，核实 Worker、PR 和现场后继续 | 文档与记录版本、实际用户决定来源、下一步和暂停状态 |
| 已有明确授权或 Operator 暂停任务 | 保留既有授权和暂停限制，公共模板更新不重开全部决定，也不恢复暂停任务 | 当前项目的授权和暂停事实；其他项目不继承权限 |

## 隔离执行的边界

作者在可丢弃的安装副本中使用临时 SQLite、受控 GitHub/飞书接口和本地 RPC 子进程核对实际 `AgentLoop` 与 `CodexAppServer`。源码入口和 `npm run build` 生成的编译入口分别执行以下检查，使用完整角色文件内容比较，不依赖某句规则匹配。

1. 两个隔离项目新建协调 Thread 时收到相同的完整协调者模板，各项目仍有自己的指导。
2. 在安装副本中替换角色文件后，同一 Runtime 和两个原 Thread 读到更新后的完整内容，无需重启 Runtime 或新建 Thread。
3. Worker 与 verifier 新建时均收到完整 Worker 模板。
4. 关闭并重开 SQLite 后，保留的协调 Thread 收到当前模板和对应项目指导，不使用 Task 中刻意保存的旧 prompt 快照，也不另建 Thread。
5. 需求记录的版本关联、来源和范围文本跨 SQLite 重开保留。
6. 实际 Codex 适配器对受控子进程发送的 `thread/resume` 含替换后的完整 `developerInstructions`，后续 `turn/start`、`turn/steer` 含完整当前 Runtime 指导。

两个入口的上述检查均通过，类型检查、构建和 `git diff --check` 通过。运行脚本、日志和模板摘要随作者交接提供，独立 verifier 应针对实际提交和基线复核。仅提示词和文档发生变化，没有运行与此无关的昂贵全量套件。

受控子进程只执行 RPC 协议，不调用真实模型。场景矩阵未做真实 Agent 行为验收；这些结果证明模板的读取、持久记录与投递路径，不能证明模型总会遵守约定。没有连接真实项目群、改动正式数据库、恢复暂停任务、部署或重启服务。正式实例和其他安装实例是否收到模板，需要各自发布后另行核对。
